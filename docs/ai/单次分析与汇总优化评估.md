# 单次分析与汇总优化评估

2026-10-03。依据当前源码、九月冻结原文、10月1–2日保存的 DeepSeek-V4.1-Flash 真实响应，以及本轮离线回放。本文是优化方案和实验记录，尚未改写生产生成逻辑。

后续已实施并恢复 Docker，完成四次真实模型调用；最新状态见[实施与实测](./2026-10-03-实施与实测.md)。下文保留为实施前的评估依据，不能用其中“尚未改写”“Docker未启动”描述最新状态。

## 结论

推荐保留三个业务阶段：轻量初筛 → 每篇全文一次分析并保存 → 基于单篇记录一次生成完整周期报告。五个阅读栏目是同一报告的五个视图，不必对应五次模型调用。

省成本的优先级：取消小错误触发整份重写；缩小重复发送的汇总材料；合并五栏目编排；记录并利用输入缓存；最后再调思考强度。不要先截断负责完整摘要的正文。

## 当前到底怎样运行

- 当前周期入口使用 `BriefingScopeService` 的 v2 标题初筛：每批20期，只输入标题、节目名和已有简介；简介最多1500字符。`uncertain`保留。旧文档里的全文分块筛选并非现在这个入口的实际调用路径。
- 入选节目使用 `EpisodeAnalysisService`：完整原文一次生成 takeaway、points、quotes、concepts、resources；每篇成功即保存，单篇、周报、月报复用。
- 正常情况下单篇只有一次模型调用；但校验失败时 `_model_call`会带回整份失败回答，要求重新输出完整JSON，最多两次。
- 汇总五栏目仍分别调用 `_generate_one`；每次传相同材料，system提示词不同，最多3个并发。并发减少等待，不减少token。
- 旧研究路径的分块摘录、观点提取、单篇整理仍存在，不能把旧记录与新周期流程混成一个成本结论。

对应源码：`backend/app/services/briefing_scope_service.py`、`episode_analysis_service.py`、`briefing_modes_service.py`、`briefing_lab_service.py`。

## 1. 筛选需要原因和全文吗

原因有两个实际消费者：材料弹窗的“筛选依据”，以及汇总输入的 `reading_focus.relevance`。它属于解释和选题线索，不是生成摘要必需的原文证据。

建议：入选只返回id和决定；排除、不确定可带一句短原因。原因不再重复进入每个汇总栏目。不要为所有入选节目写一段解释，也不要为筛选专门提取原话。

不需要全文筛选。现有标题＋简介已经比前3000词更便宜。标题不明确时可以选择：直接保留；或补读少量开头、中段、结尾。若目标是宽松排除，直接保留通常更简单。

仅用开头3000词做排除有漏选风险：长节目开头可能是广告、嘉宾背景，相关议题在后面。补读只能帮助判断，不能把“样本里没看到AI”当作全文无关。英文词、中文字符、模型token应分别计量。

## 2. 当前摘要是否合理

完整核对样本：27分钟、25,178字符的《Trillion Token Context》。当前takeaway覆盖统一物理模型、四维轨迹、神经算子、共享学习及PDE反馈，适合作导读。主要应用半导体与能源、多尺度训练和计算开销等需要读下面的11个议题才能获得。

所以问题不只是240字太少：产品应明确区分“导读”和“完整分议题摘要”。完整摘要应覆盖重要议题及关键条件，不要求复制每个问题、每个细节。1–12个议题的硬上限也未必适合所有两三小时访谈。

现有样本还有两个编辑问题：多个议题重复写大集群/高分辨率等条件；有些“团队采用的做法”被写成普遍必要条件。逐字引文检查无法解决这类语义问题。

建议单篇保存五块：短导读、分议题摘要、少量精选原话、新词方法、提到的资料。标题和正文长度以阅读目标引导，不因超过几字重跑。议题中自然保留理由、案例与限制，避免每项强制填出一条空泛boundary。

## 3. 引文应承担什么职责

- 分议题摘要：通过原文段落ID定位来源，点击后由程序回填原文；不为每个观点再生成一份长引文、翻译和语境。
- 精选原话：保留逐字引用与必要译文，因为原话本身就是阅读对象。
- 共性与分歧：引用对应的单篇议题ID；做比较时保留条件，确有歧义再读取那几个原文段落。

“引文存在”只证明文本可定位，不能单独证明概括受它支持。段落编号也只能提供定位，不是语义正确性的证明。段落及偏移由程序稳定生成，和正文哈希绑定，避免文稿更新后引用错位。

## 5. 汇总只做一次

输入为每篇稳定的议题记录和候选项短ID。一次请求输出：核心提要、原话选择ID、概念去重ID、资料选择ID、跨篇联系。服务器根据ID回填已保存原话、译文、说明与出处。

原话、概念、资料多数是选择和去重，无需在五次调用里重写全部文本。共性与分歧才是主要跨篇推理任务。单篇失败不撤销其他篇，汇总中某一项错误也不撤销整篇结果。

若用户仅生成一个栏目，可以按需生成该栏目；生成完整简报默认一次编排。不要为了批量省输入强迫只读一个栏目的用户生成全部。

研究依据：[Query-OPT（EMNLP Industry 2024）](https://aclanthology.org/2024.emnlp-industry.86/)直接比较相同会议输入的单问题与多问题提示词，支持用合并问题减少重复推理请求。其模型和任务不同于本项目，是设计依据，不是本项目质量已经验证的证明。

## 6. 两种缓存要区分

业务缓存：整篇分析已保存，后续不用调用模型，是最直接的节省。现有单篇缓存已经具备；周期成品还应按材料版本、关注范围、分析/编排版本复用。主动“重新生成”才跳过成品复用，失败补跑只补缺失部分。

单篇基础解读不要绑定用户这次选的关注话题。用户从“AI”改为“算力”时，重新筛选和组织已有议题即可；只有原文或分析规则变化才需要更新单篇记录。周报和月报直接引用同一批单篇记录，月报不只依赖已被压缩过的周报。

输入缓存：仍然调用模型，只降低重复前缀的输入成本，输出及思考仍收费。当前五模式在system提示词处就不同，后面即使放同一大段材料，也不能据此认为能命中全文前缀。

推荐消息顺序：稳定公共规则 → 稳定、排序一致的材料 → 本次任务。不要在前面塞当前时间、随机ID和不断变化的进度。若经AI Ping路由，缓存命中还受实际服务商影响，不能直接假设享受DeepSeek官方缓存机制/价格。

当前 `LLMClient.chat`只保留prompt/completion/total，丢失cache和reasoning明细，无法从当前分析记录验证缓存收益。应透传cached_tokens、cache_miss、reasoning_tokens、provider、finish_reason、可见输出长度；不同供应商缺失字段标为未知，不伪造为0。

旧36篇第一尝试的缓存记录为4,224/349,795输入token，约1.21%。它们输入是不同节目，低命中率本身不是bug，也不是五模式缓存效果的实测。

依据：[DeepSeek缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)、[AI Ping文本API](https://aiping.cn/docs/API/text-models)。缓存是尽力命中，不保证固定折扣。AI Ping支持部分模型的 `enable_thinking`，是否对当前Flash生效必须检查真实返回。

## 7. 用少量评估替代复杂质量门

[SummEval](https://aclanthology.org/2021.tacl-1.24/)、[DialSummEval](https://aclanthology.org/2022.naacl-main.418/)重视一致性、相关性、连贯性、流畅性；[会议摘要指标研究](https://aclanthology.org/2024.findings-emnlp.393/)指出自动指标会掩盖遗漏和对话语境问题。

本项目先用四个可人工核对的问题：

1. 主要议题是否覆盖，包括后半段；广告寒暄是否被排除？
2. 判断、案例、数字、条件、发言归属是否忠于原文？
3. 每段是否具体、易读，重复观点是否合并？
4. 引用是否能定位；分歧是否真在讨论同一命题？

线上只保留JSON可解析、引用ID存在、精选原话可回填、任务成功/失败和成本记录。长度不合适在展示层处理；个别引用失败局部省略或标注，不因它重跑整个全文。不默认再用一个大模型给每篇打分。

# 短期路线图

> 目标：先把产品全流程稳定跑起来，服务一小部分早期用户；暂不做复杂企业权限、计费和大规模成本模型。

## 当前阶段目标

把核心闭环做稳定：

```text
用户登录 -> 添加 RSS -> 选择单集 -> 下载音频 -> 转录 -> AI 摘要 -> 保存结果 -> 回看/分享
```

短期判断标准不是功能数量，而是这个流程能否稳定完成、失败时是否可理解、结果是否可再次访问。

## 核心事项

1. 基础用户隔离
   - 添加用户账号。
   - `feeds`、`episodes`、`transcripts`、`summaries`、`tasks`、`settings` 增加 `owner_id`。
   - 所有用户数据查询都按 `owner_id` 过滤。
   - 暂不做复杂组织、团队、RBAC 权限矩阵。

2. 管理员账号
   - 需要管理员账号，但短期只做最小管理员能力。
   - 管理员用于系统维护、用户排查、查看任务状态和处理异常。
   - 管理员默认不应该直接编辑普通用户内容，避免权限边界混乱。

3. 设置中心完善
   - 默认转录 provider。
   - 默认转录语言。
   - Whisper 模型和模型目录。
   - LLM API endpoint / key / model。
   - AssemblyAI API Key。
   - Hugging Face Token。
   - 明确标记哪些设置修改后需要重启后端。

4. 全流程稳定性
   - 下载中、转录中、摘要中状态要准确。
   - 任务失败要展示明确原因。
   - 任务历史可以跳转回对应单集。
   - 避免重复下载、重复转录、重复摘要。

5. 本地转录优先策略
   - 官方字幕优先。
   - 本地 `faster-whisper` 作为主要转录方式。
   - 默认本地转录并发为 1，避免机器资源被打满。
   - 云端 API 作为可选能力，不默认消耗。

6. 基础分享与回看
   - 每一集有稳定 URL。
   - 登录用户可以复制自己的单集链接。
   - 公开分享后续单独做 `/share/:token`，不要直接暴露私有 episode URL。

## 账号与权限设计

短期建议只做两类账号：

| 角色 | 用途 | 权限 |
| --- | --- | --- |
| 普通用户 | 正常使用产品 | 管理自己的订阅、单集、转录、摘要、设置和任务 |
| 管理员 | 系统维护和排查问题 | 查看用户列表、查看任务概况、查看系统诊断、禁用异常用户 |

不建议短期做更多角色。原因是当前目标是跑通产品闭环，复杂角色会增加开发量，也会让每个 API 都要提前承载更复杂的权限规则。

## 权限边界

普通用户必须只能访问自己的数据：

```text
resource.owner_id == current_user.id
```

管理员可以看系统层面的信息，但短期不要默认拥有“随意修改用户内容”的能力。更合理的做法是先提供：

- 用户列表。
- 用户状态：启用 / 禁用。
- 每个用户的订阅数量、任务数量、占用空间等统计。
- 全局任务队列状态。
- 系统诊断：MongoDB、模型、转录 provider、LLM 连接状态。

如果以后需要管理员代用户排查内容，可以增加受控的“以用户身份查看”功能，并记录审计日志。

## 测试账号建议

开发和测试时固定准备三个账号：

| 账号 | 角色 | 用途 |
| --- | --- | --- |
| `admin@example.com` | 管理员 | 测试管理后台、系统诊断、用户列表 |
| `user1@example.com` | 普通用户 | 测试正常完整流程 |
| `user2@example.com` | 普通用户 | 测试数据隔离，确认看不到 user1 的数据 |

测试时重点验证：

- `user1` 添加的 feed，`user2` 看不到。
- `user1` 的 episode 链接，`user2` 不能直接访问。
- `user1` 的 task 历史，`user2` 看不到。
- 普通用户访问管理员接口会被拒绝。
- 管理员可以进入管理页，但不会混入普通用户的个人工作台。

## 暂时不做

这些内容有价值，但不属于短期核心：

- 企业组织 / 团队权限。
- 复杂 RBAC 权限矩阵。
- 计费和套餐。
- 大规模 API 成本评估。
- 多 worker 调度。
- 公开分享权限细分。
- 完整知识库系统。

这些应在核心流程稳定、有早期用户反馈之后再做。
